# OpenSession — implementation plan

One Cloudflare Worker (`website`), Spiceflow RSC for pages + API, D1 (SQLite) via drizzle
beta from a `db` workspace package, R2 for files, `send_email` binding for mail, a cron
trigger in the same worker for reminders and the email outbox, **sigillo** for secrets.
Skeleton, auth, org layer, and component patterns are copied from **akarso**
(`~/.kimaki/projects/akarso`); the org/auth part of `schema.prisma` is already a 1:1 port
of `akarso/db/src/schema.ts`.

The build order (milestones at the bottom) is chosen so a demoable end-to-end slice —
verified login → create event → publish CFP MDX form → public submit → abstracts table →
accept → portal task — works early, then agenda, emails/ICS, and embeds layer on top.

```
                       ┌──────────────────────── website worker ────────────────────────┐
  Browser ───────────► │ Spiceflow app (src/app.tsx)                                    │
   admin dashboard     │  ├─ pages (RSC): /org/:orgId/e/*  /submit/*  /portal/*  /embed/*│
   public CFP form     │  ├─ API: /api/auth/* (BetterAuth)  /public/:slug/*.json|.ics   │
   speaker portal      │  ├─ server actions (src/actions.tsx)                           │
                       │  └─ scheduled(): close forms, reminders, outbox, file GC       │
                       └──────┬──────────────┬──────────────┬────────────────┬──────────┘
                              ▼              ▼              ▼                ▼
                         D1 (drizzle     R2 bucket      send_email      sigillo-injected
                         via db pkg)     (File bytes)   binding          secrets (dev)
```

## 2. db package: drizzle schema + migration

### Translation rules (schema.prisma → src/schema.ts)

- `drizzle-orm@beta` + `drizzle-kit@beta`, namespace imports (`import * as s from
  'drizzle-orm/sqlite-core'`), snake_case column names, `@@map` names respected
  (`session` = BetterAuth, `event_session` = domain session).
- IDs: `s.text('id').primaryKey().$defaultFn(() => ulid())`.
- Timestamps: the akarso `epochMs` customType (Date-accepting `toDriver`), copied verbatim.
- Enums: `s.text('col', { enum: [...] })` with the exact values from schema.prisma
  (lowercase for the org layer, UPPERCASE for domain enums). Types derived via
  `$inferSelect`, never duplicated.
- Relations: one `defineRelations` block at the bottom covering both directions of every
  relation (needed for `db.query` `with`).
- Every event-scoped parent gets `s.unique().on(table.id, table.eventId)` as the target
  for composite tenant-boundary FKs.

### Appendix constraints — all expressible in drizzle, no hand-written SQL needed

The schema.prisma header appendix lists what Prisma cannot express. Drizzle can express
all of it in the table config array, so the generated migration carries them:

| Constraint | Drizzle construct |
|---|---|
| Partial uniques (task_assignment ×2, form_field_value ×2, speaker userId, org personal) | `s.uniqueIndex('name').on(...).where(orm.sql\`...\`)` (akarso already does this for `org_owner_personal_unique`) |
| CHECKs (session title/time-range, review rating 1..5, enum value CHECKs on status columns) | `s.check('name', orm.sql\`...\`)` |
| Composite FKs on nullable columns (session→track/format/room/form/submitter, task_assignment→session) | `s.foreignKey({ columns: [...], foreignColumns: [...] })` with `.onDelete(...)` |

Enum CHECKs: add `CHECK (status IN (...))` checks for every lifecycle enum column
(SQLite text enums are TypeScript-only). Keep the CHECK list next to the enum array so
they cannot drift.

### Entrypoints

Follow the drizzle skill's cloudflare.md canonical pattern (akarso's `workerd.ts` now
matches it too — it was switched off the buggy `drizzle-orm/d1` driver):

- `db/src/workerd.ts` — `drizzle-orm/sqlite-proxy` with inline D1 callbacks
  (`stmt.raw()`, `get` returns `rows[0]`, batch via `env.DB.batch`). Same code akarso has
  in `website/src/db.ts`; we lift it into the db package so the website just re-exports.
- `db/src/node.ts` — sqlite-proxy over the Cloudflare D1 HTTP API
  (`CLOUDFLARE_ACCOUNT_ID/DATABASE_ID/D1_TOKEN`), used by `scripts/seed.ts` and one-off
  scripts.
- `package.json` exports: `{ ".": { "workerd": "./src/workerd.ts", "default":
  "./src/node.ts" }, "./schema": "./src/schema.ts" }`. Website tsconfig gets
  `customConditions: ["workerd"]`.

### Migration workflow

1. Write `schema.ts` fully (all 23 models + constraints above).
2. `pnpm drizzle-kit generate` → review `drizzle/<ts>_initial/migration.sql`; verify the
   partial-unique WHERE clauses, CHECKs, and composite FKs came through; add comments.
3. `wrangler.jsonc` D1 binding uses `migrations_dir: "../db/drizzle"` and
   `migrations_pattern: "../db/drizzle/*/migration.sql"` (nested layout, like akarso).
4. Apply with `wrangler d1 migrations apply DB --local | --remote [--env preview]`;
   deploy scripts run migrations first (see §12).
5. A `db-migrations.test.ts` (ported from akarso) applies the real SQL to `node:sqlite`
   `:memory:` and asserts the schema loads — plus new assertions that the partial uniques
   and CHECKs actually reject bad rows.

Loader/layout stack for admin pages:

| Level | Loader returns | Layout renders |
|---|---|---|
| `/*` | `{ session }` | `<html>` shell + ProgressBar |
| `/org/:orgId/*` | org, my role, my orgs (switcher data) — 404s non-members before anything leaks | — |
| `/org/:orgId/e/:eventId/*` | event (validated `event.orgId === params.orgId`), tracks/formats/rooms, sidebar badge counts | `EventShell` sidebar |
| page-level loaders | table data per §5 tab | page |

`router.href('/org/:orgId/e/:eventId/abstracts', { orgId, eventId, status: 'pending' })`
gives compile-checked links for every sidebar item and tab; renaming a route or tab
value breaks `tsc`, not production.

### Event admin — `/org/:orgId/e/:eventId/*`

- `.loader('/org/:orgId/*')` resolves org + membership + the caller's org list in ONE
  query (`db.query.org.findFirst({ where: { orgId }, with: { members: … } })`, derive
  `me` from the member list); non-members get 404 before any data leaks.
- `.loader('/org/:orgId/e/:eventId/*')` fetches the event with tracks/formats/rooms and
  sidebar badge counts, validating `event.orgId === params.orgId` (plus the DB-level
  composite FKs guarantee children can't cross events).
- `.layout('/org/:orgId/e/:eventId/*')` renders `EventShell` (sidebar).

Screens per route are in the hierarchy tree above; per-tab features in §5. Sidebar item
= route; tab = query param (`?status=`, `?tab=`, `?view=`) so tabs are linkable,
type-safe via each page's zod `query` schema, and switch client-side with `router.push`
without remounting the shell. Screenshot refs: dashboard img 34-36, abstracts img
19-23, forms img 05-15, agenda img 24, tasks img 25.

## 6. MDX forms: render, validate, submit

The whole form is one MDX source per immutable `FormVersion` (live = newest version).
safe-mdx renders it with `{ values, tracks, formats }` in scope; conditional logic uses
`<Show when={expression}>` because safe-mdx does not evaluate JSX nested inside a
JavaScript expression. Attribute expressions are evaluated by safe-mdx's AST interpreter
with function and method calls explicitly disabled on both client and server.

### Default forms created with every event

The form engine stays fully generic, but organizers should not begin from an empty form
library or rebuild fields that every conference needs. `createEvent` pre-generates the
event id, three form ids, and three version ids, then inserts the event and the following
forms + first immutable `FormVersion` snapshots in one `db.batch`:

| Default form | Purpose / target | Initial status | Why it exists |
|---|---|---|---|
| **Call for Papers** | `CFP / SUBMISSION` | `DRAFT` | Title, abstract, track, format, event-specific questions, and `<Participants>`. Organizer reviews copy/settings, then opens it publicly |
| **Speaker Profile** | `PORTAL / SPEAKER` | `OPEN` | The standard profile every event needs: first/last name, email, bio, job title, company, pronouns, headshot, website, LinkedIn, X/Twitter |
| **Session Materials** | `PORTAL / SUBMISSION` | `OPEN` | Cover image, presentation/slides upload, final A/V requirements, and other accepted-session material |

These are normal MDX forms, not special schemas or hardcoded React forms. Organizers can
edit their wording, required flags, conditional sections, and add custom questions. The
default names that feed typed columns are reserved (next section); removing or renaming
one produces the editor's field-contract warning. A default form can be deleted only
before it has responses, exactly like a manually created form.

Acceptance creates standard assignments from these defaults: **Complete Speaker
Profile** targets each speaker and **Upload Session Materials** targets each accepted
submission. Events can add optional FORM tasks for less common workflows such as travel,
dietary needs, visas, release agreements, or hotel details. Confirmation remains a
first-class participation action, not a custom form.

### Field component library (`name` prop = data contract)

Server-compatible components map (NOT exported from a `'use client'` barrel — RSC trap):
each interactive field lives in its own `'use client'` file; the map module has no
directive.

| Component | Props | Behavior |
|---|---|---|
| `<TextField>` | name, label, required, maxLength, placeholder, multiline | text/textarea |
| `<RichText>` | name, label, required, maxLength | textarea MVP (rich text later) |
| `<Select>` | name, label, options (from scope: tracks/formats or inline array), required, multiple | multi = one FormFieldValue row per value |
| `<Checkbox>` / `<Radio>` | name, label, options | |
| `<FileUpload>` | name, label, accept, required | uploads via `/api/upload`, stores fileId as value |
| `<Participants>` | min, max | repeats children per participant entry; children `name`s prefixed `speaker.*` are stored with `subjectSpeakerId` |
| `<Section>` / `<Info>` | title / children | layout + copy |

Free markdown between components is the welcome copy / instructions (replaces the
wizard's WYSIWYG screens).

### Client render (public CFP + portal forms)

`form-renderer.tsx` (`'use client'`): receives `mdxSource` + scope data from the loader,
parses with `mdxParse` (browser-safe), holds `values` state (+ participants array), and
renders `<SafeMdxRenderer components={fieldComponents} scope={{ values, tracks, formats }} />`.
Field components read/write values through a React context keyed by `name` (with a
participant-index prefix inside `<Participants>`). Every value change re-renders, so
`<Show when={values.format === 'workshop'}>…</Show>` conditionals are live. Autosave
debounces a `saveDraft` server action (FormResponse DRAFT + Session DRAFT for CFP).

### Server-side re-validation (`collect-fields.ts` + `validate.ts`)

On submit the server re-renders the response's **pinned** `FormVersion.mdxSource` with
the submitted values in scope, using `MdastToJsx` with a **collector components map**:
each field component is a plain function that pushes `{ name, required, maxLength,
options, type, participantScope }` into an array and returns null (`<Participants>`
recursion runs children once per submitted participant). This yields exactly the fields
the user SAW under the same conditional logic. Then validate:

- unknown submitted names → reject; missing required visible fields → reject
- maxLength, option membership (library options validate against real track/format ids)
- `visitor.errors` (expression/missing-component) → reject with line numbers
- hard-coded submission limit: 3 per user per event (counting drafts)

On success, one `db.batch`: mark response SUBMITTED, insert FormFieldValue rows, copy
well-known names to typed columns (`title/description/track/format` → Session,
`speaker.*` → Speaker rows + SessionParticipants), Session DRAFT → PENDING with
`submittedAt`, enqueue `SUBMISSION_CONFIRMATION` email.

### Well-known fields and the public data projection

Every answer is always preserved in `FormFieldValue`, pinned through `FormResponse` to
the exact `FormVersion` that displayed it. A hardcoded registry in
`well-known-names.ts` additionally projects common answers into typed columns:

| Reserved form names | Typed destination | Used by |
|---|---|---|
| `title`, `description`, `track`, `format`, `coverImage` | `event_session` title/description/trackId/formatId/coverImageFileId | Abstracts and sessions tables, agenda block/popover, public schedule, embeds, JSON/ICS feeds |
| `speaker.firstName`, `speaker.lastName`, `speaker.email`, `speaker.bio` | `speaker` identity/profile columns | Portal profile, admin speaker detail, agenda speakers, speaker embed |
| `speaker.jobTitle`, `speaker.companyName`, `speaker.pronouns` | `speaker` profile columns | Agenda/session popover, speaker cards and embeds |
| `speaker.headshot`, `speaker.websiteUrl`, `speaker.linkedinUrl`, `speaker.twitterUrl` | `speaker` file/link columns | Speaker profile and public speaker cards |

The typed rows are the **current stable projection** used by product UI. Submitting the
default Speaker Profile form patches the linked Speaker row; submitting a CFP creates
the initial Speaker and Session projections. Later profile/material submissions update
only the well-known fields present in that form. Responses and field values remain the
immutable history and hold every custom answer.

Public surfaces never guess which arbitrary custom questions are safe to display. The
agenda block and its click popover read the typed projection only: title, description
excerpt, track, format, room/time, cover image, and participant name/headshot/job title/
company. The agenda and speaker embeds use the same projection and expose only
`ACCEPTED + PUBLIC` sessions. Custom values (dietary, travel, internal notes, release
answers) stay private and appear only in authenticated admin/session/task detail views
unless a future explicit display setting is added.

### Editor + versioning

`/org/:orgId/e/:eventId/forms/:formId`: Monaco left, live preview right (same renderer with sample
scope), settings drawer. Save = insert new `FormVersion` (immutable); the editor diffs
field `name`s between the previous and new version and warns when a name disappears.
New events seed all three templates from `starter-template.ts`. Additional forms start
from the template matching their purpose/target (CFP, speaker, or submission materials)
instead of an empty document.

**FUTURE (do not build now):** an AI chat that edits the form MDX from a prompt ("add an
input for the user phone number"). The editor is already API-driven — "create new
FormVersion from mdxSource" is a single server action — so an AI endpoint can later
generate a new version and reuse the same validation/preview pipeline unchanged.

## 7. Auth flows (one identity system, two populations)

- **Config** (`src/db.ts`, akarso `getAuth()` shape): `better-auth/minimal` +
  `better-auth-drizzle-adapter` (sqlite), verified email/password accounts, Google provider
  with `prompt: 'select_account'`, `session.expiresIn` 1y + cookieCache, and `onAPIError` logging.
- **Admin flow**: `/login` → email or Google → `/dashboard` resolver → `ensurePersonalOrg`
  (race-safe via the partial unique, ported verbatim from akarso) → newest event or org
  page. Org-level authz only: every OrgMember manages/reviews every event of the org.
- **Participant flow (portal magic of shared login)**: public CFP and portal use the same
  verified identity. `lib/speaker-link.ts` runs in the portal/submit loaders: given a session
  with a verified email, find `speaker(eventId, email)` — if it exists with `userId
  NULL`, claim it (guarded by the partial unique `(eventId, userId) WHERE userId IS NOT
  NULL`); if none exists on first CFP submit, create it. Co-speakers added by email get
  `userId NULL` Speaker rows that auto-link on their first sign-in with that email.
- One `User` can be both: an org admin who submits a talk to another org's event just
  gets a Speaker row there.
- Server actions and API routes always re-check authz; loaders never leak data before
  the membership/ownership check resolves.

## 8. Submissions, review, decisions

- Status transitions live in `lib/submissions.ts` as a single guarded function
  (validates legal edges of the state machine in database-schema-plan.md, stamps
  `submittedAt/decidedAt/withdrawnAt`).
- Each EVALUATION form is one round. Its newest `FormVersion` defines the scorecard;
  submitted reviews pin the version through `FormResponse`. `Review` owns assignment and
  recusal, while `EvaluationReviewer` scopes the reviewer pool to one round. Weighted
  aggregates and progress are derived from submitted field values.
- Accept/decline queues: bulk-select rows → move to `ACCEPT_QUEUE`/`DECLINE_QUEUE` →
  "Notify" action per queue: for each session set final status, enqueue
  `DECISION_ACCEPTED/DECLINED` (dedupeKey `decision:{sessionId}:{speakerId}`), stamp
  `notifiedAt` only after the outbox row reaches SENT, and on acceptance run
  `lib/tasks.ts` auto-assignment: for every TaskDefinition create TaskAssignments
  (SPEAKER-target → per confirmed participant speaker, SUBMISSION-target → per accepted
  session×speaker) with `onConflictDoNothing` against the partial unique indexes, and
  enqueue `TASK_ASSIGNED`.

## 9. Agenda

- The live schedule IS `Session.roomId/startsAt/endsAt` — no drafts.
- Views: **list** (table with times/room/track, sortable), **week** (all event days in
  compact columns), and **room grouping** via query param. Unscheduled ACCEPTED (+
  SERVICE) sessions remain available in List and Rooms. Placing or moving an item opens
  a drawer pre-filled with `Format.defaultDurationMinutes`.
- `lib/conflicts.ts` (pure, heavily unit-tested): sessions conflict when time ranges
  intersect AND (same room OR shared participant). Computed in the agenda loader, shown
  as warnings in agenda views and a conflicts panel; placement that creates a conflict asks
  for confirmation, never blocks.
- Schedule changes bump `icsSequence` and enqueue `SCHEDULE_INVITE/UPDATE/CANCEL` per
  confirmed participant (dedupeKey `ics:{sessionId}:{speakerId}:{icsSequence}`).
- SERVICE sessions (breaks/lunch) created from the agenda directly (kind=SERVICE, no
  speakers/CFP).

## 10. Emails + ICS

Per the transactional-email skill: **plain HTML template strings** (dedent), Gmail-like
styling, dark-mode block, reply_to always set (sender domain + reply-to recorded in
AGENTS.md once the user picks them — placeholder until then). NO React email rendering.

- `templates.ts`: one `build{Kind}` function per `EmailKind` (9 kinds) returning
  `{ subject, html, text }`. `scripts/preview-emails.ts` renders all to `tmp/` for
  Playwriter light/dark screenshots.
- `send.ts`: `enqueueEmail({ kind, dedupeKey, to, speakerId?, sessionId?, ics? })`
  inserts the EmailMessage row (`onConflictDoNothing` on dedupeKey = the idempotency
  gate), then tries an immediate send via `waitUntil`; the cron drains QUEUED/FAILED rows
  (attemptCount capped, retry on the same row).
- Sending: `env.EMAIL.send({ from, replyTo, to, subject, html })` for plain mail. For
  ICS mail, build raw multipart MIME with `mimetext` (html part + `text/calendar;
  method=REQUEST|CANCEL` part) and send via `new EmailMessage(from, to, raw)` from
  `cloudflare:email` — the builder overload has no attachment support.
- `lib/ics.ts` (pure, snapshot-tested): VEVENT with stable UID
  `session-{sessionId}@{appDomain}`, SEQUENCE from the message snapshot, METHOD
  REQUEST/CANCEL, ORGANIZER = sender, DTSTART/DTEND in UTC with event-tz DTSTART
  fallback. Also reused by `/public/:slug/schedule.ics`.
- Reminder offsets hard-coded in `reminders.ts`: task due −3d, −1d, overdue; CFP draft
  −3d/−1d before `Form.closesAt`. Dedupe by day in the key.
